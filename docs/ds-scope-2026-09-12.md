# What the design system is missing, and where the SDK components belong

Written 2026-09-12, from `main` at `91e61fa`. Every number below was measured on this checkout on
that date, by the command printed beside it. Where a claim is not measured, it says so.

This document answers four questions Olcay asked:

1. What's next?
2. What's missing, in terms of design system?
3. Should the SDK components become examples rather than part of the design system?
4. Could card layouts with slots remain? What about onboarding or notification overlays?

## 0 · The short version

**Yes to examples, but not yet, and not by deleting anything.** 14 of the 24 Product/SDK sets are
compositions a product could assemble; 9 are genuine primitives; 1 is already a slotted layout. But
every one of the 24 carries Code Connect on three platforms pinned to a Figma node ID, and a Figma
component set cannot be deleted and recreated without losing that ID. So the move is a
**deprecation, not a deletion**, and it is blocked behind roughly eight missing parts — without
them an "example" is a pile of hand-drawn divs, not a composition of design-system components.

**Yes to slotted card layouts** — it is the strongest of the three ideas — with one hard blocker:
**not one Product/SDK set has a real Figma slot.** `productSdkSlot()` returns a frame.

**Notification overlays yes, onboarding not yet.** The in-surface status message has been the #3
ranked missing primitive since 2026-09-05 and the MAP-595 prototype hand-built it four times.
Onboarding has one consumer, once.

**And two things that outrank all of it.** Nothing outside this monorepo consumes Kozmos (§1). And
every overlay entrance animation in the library is dead CSS — eight components reference
`animate-in` classes that no plugin generates (§4.5).

## 1 · The finding that reframes the question

| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| all five packages at `v0.0.1`                                | `for p in packages/*/package.json; do node -e 'console.log(require(process.argv[1]).version)' ./$p; done` |
| zero git tags                                                | `git tag \| wc -l`                                                                                        |
| `.changeset/` holds only `config.json`                       | `ls .changeset`                                                                                           |
| release workflow skips npm publish unless `NPM_TOKEN` is set | `.github/workflows/release.yml:67`                                                                        |
| every dependant of `@kozmos/react` is inside this repo       | `grep -rl '"@kozmos/react"' --include=package.json . \| grep -v node_modules`                             |

Six dependants: `packages/vue`, `packages/react`, `apps/docs`, `apps/playground-vue`,
`apps/playground-web`, `apps/mapscale-review`. The iOS package is consumed by one playground; the
Android package by one playground.

Two further findings from the audit sweep, which read outside this repo (recorded here as
**reported, not re-verified in this document**):

- The shipped Pointr Web SDK v10.7.1 stylesheet, fetched from the public CDN (979,502 bytes),
  contains **zero occurrences of "kozmos"**. It implements the product's own `--pointr-*` tokens.
- There are three Kozmos-named Figma libraries, and they disagree on the brand blue: PDS Core's
  toggle track is `#346df1`, Kozmos DS - Core Library's primary button is `#0d44c2`.

This agrees with the ruling already recorded in `memory/kozmos-token-roles.md`: on 2026-09-11 the
MAP-595 file was moved back onto the **product's** four-mode Primitive Tokens, because "our current
implementation uses these exactly". A 2026-09-10 attempt to bind it to Kozmos DS roles — 1,559
paints — cost a day to reverse.

**So the largest gap in the design system is not a component.** It is that the system has no
consumer outside its own repo, and the one product surface that exists deliberately does not use its
tokens. Every recommendation below is worth less than settling that. Two honest options:

- **Ship it.** Publish `v0.1.0` to a registry the Web SDK and the Dashboard can install, and get one
  real consumer. Then the missing components below are decided by that consumer, not by a taxonomy.
- **Name it internal.** Accept that Kozmos is a reference implementation and a Figma library, and
  stop paying four-platform parity costs for components nobody installs.

Everything in §3–§6 assumes the first. Under the second, most of it is optional.

## 2 · Should the SDK components become examples?

**Yes in principle — it is already the written policy, twice** — but the move has a price nobody has
costed, and it is blocked behind missing parts.

`docs/figma-upcoming-components.md` (2026-08-30) states _"Primitives, not screens"_: the library
ships parts with slots, products assemble screens. `docs/sdk-module-primitives.md` (2026-09-05)
states _"an SDK module is a composition, not a component"_. The 24 sets were built anyway.

### 2.1 · The per-set verdict

From an agent audit of all 24 sets (one agent per set, reading web + Figma painter + iOS + Android +
consumers). **These verdicts were not adversarially verified — see §7.**

| verdict                | n   | sets                                                                                                                                                                                                                               |
| ---------------------- | --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| move-to-examples       | 14  | BrowseCategoriesPanel, DirectionStep, FeedbackCard, MapControlsGroup, POICard, POIDetailPanel, POIResultCard, POIResultList, RouteOptionCard, RoutePreviewPanel, RouteSummary, RoutingInputGroup, SaveLocationCard, WayfindingCard |
| keep-as-primitive      | 9   | CategoryTile, DynamicIsland, FloorSelector, LocationPin, MapControlButton, MapOverlay, MapView, POIMediaGallery, UserLocationMarker                                                                                                |
| keep-as-slotted-layout | 1   | AdaptiveMapShell                                                                                                                                                                                                                   |

Of the 14, most have no consumer at all. The ones that do appear once each in a playground with
no-op handlers — `MapControlsGroup` is mounted with four `() => {}`.

The seven the audit classed as **product-layout** (encoding which facts to show, in what order) are
the safest to move: POIDetailPanel, POIResultCard, RouteOptionCard, RoutePreviewPanel, RouteSummary,
RoutingInputGroup, SaveLocationCard.

### 2.2 · The gallery already exists, and already obeys the rule

Both homes exist and neither is the problem:

- **Figma**, page `Examples` (`286:1601`): six `Example /` frames. `Example / SDK Route Flow` is
  built from Button, Badge, SearchBar, Progress, List and BottomNavigation — **not one Product/SDK
  set**. Read the builder at `figma/foundations-importer/code.js:11131-11329`.
- **Storybook**, `apps/docs/stories/examples/`: one file, `MapSearch.stories.tsx`, titled
  `Examples/Map Based Search`, composing Badge, Button, Card, Input. Dated February.

So this is not a mechanism to build. It is a gallery that has been sitting nearly empty while 24
library components were built beside it.

### 2.3 · What moving a set actually costs — measured

This is what my earlier advice missed. Every one of the 24 sets has Code Connect on **all three**
platforms, each pinned to a Figma node ID:

```
$ for n in <24 names>; do ls packages/react/src/components/$n/$n.figma.tsx \
    packages/ios/Sources/Components/$n/$n.figma.swift; find packages/android -iname "$n.figma.kt"; done
  AdaptiveMapShell   web:1 ios:1 android:1   node-id=1351-7985
  POIDetailPanel     web:1 ios:1 android:1   node-id=1351-8103
  … 24 of 24, three of three
```

**72 Code Connect mappings, 24 pinned node IDs.** Removing one set means, in order:

1. Delete its Figma component set — **the node ID is gone permanently**. `memory/kozmos-never-rebuild-in-plugin.md` and the plugin's own rule: Update preserves node IDs, Rebuild mints new ones. There is no "move a set out and keep its ID".
2. Delete three Code Connect files, or they dangle.
3. Delete `build*/update*/rebuild*` handlers from `figma/foundations-importer/code.js` **and** its
   entry in `PRODUCT_SDK_UPDATE_SEQUENCE` — `pnpm components:contract:check` fails on any update
   handler that is in neither bulk sequence (`scripts/check-component-contracts.mjs:10300`).
4. Remove it from `COMPONENT_PAGE_LAYOUT_SECTIONS`, because `pnpm figma:verify` derives the set names
   it expects from that array (`scripts/verify-figma-library.mjs`, `function expectations()`).
5. `STATUS.md` regenerates from the component directories; the lane summary changes from 22.

### 2.4 · Recommendation: deprecate in place, never delete

Deletion is a one-way door on the node IDs. Deprecation is reversible and costs nothing:

1. **Build the missing parts first** (§4). Until they exist, an example cannot be built from
   design-system components, which is the whole point.
2. **Build the example beside the set**, in both galleries — Storybook `Examples/*` and a Figma
   `Example /` frame — composed only of Core parts.
3. **Mark the set deprecated**: a `@deprecated` JSDoc tag on the React component pointing at the
   example, and a line in the Figma set's description. Keep the set, its node ID and its Code
   Connect alive.
4. **Delete only** when a real consumer has existed and has not used it for a release cycle. Given
   §1, that clock has not started.

## 3 · Card layouts with slots

**Yes — the strongest of the three ideas, with one blocker to fix first.**

### 3.1 · The blocker, verified

```js
// figma/foundations-importer/code.js
async function productSdkSlot({ name, label, width, height, … }) {
  const slot = productSdkFrame(name, { … });   // ← a FRAME, not a SLOT node
```

All 28 `productSdkSlot` calls make frames named "… Slot". This is exactly the trap already recorded
in `memory/kozmos-frame-is-not-a-slot.md`: only a `SLOT` node can carry a slot binding; a frame named
"… Slot" reads as one everywhere except where it counts. Composition points are real on web (15 of
24 sets), iOS (`@ViewBuilder`) and Android (Compose lambdas). **In Figma they are decorative.**

Fixing this is a precondition for promising slotted layouts to designers, because the designer's
experience of a "slot" is swapping an instance in the Figma layer panel.

### 3.2 · The proposed layouts

| layout                                                                      | slots                                                                | would cover                                                                                           |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **PanelLayout** — Drawer's Header/Content/Footer API on a non-modal surface | header, body, footer; axis `Presentation = Inline \| Sheet \| Panel` | POIDetailPanel, RoutePreviewPanel, BrowseCategoriesPanel, POIResultList, WayfindingCard, FeedbackCard |
| **MediaCard** — Core Card gaining native slots                              | media, header, meta, content, actions                                | POICard, SaveLocationCard, FeedbackCard, WayfindingCard                                               |
| **ListRow** — NavigationItem's slot shape + two-line text + State axis      | leading, trailing, note                                              | POIResultCard, DirectionStep, RouteSummary, CategoryTile, RouteOptionCard                             |
| **ControlCluster** — not a card; the map lane's missing primitive           | children, orientation, dividers                                      | MapControlsGroup, FloorSelector                                                                       |
| **MapShell** — AdaptiveMapShell, promoted to real Figma slots               | map, topBar, controls, panel, status                                 | AdaptiveMapShell, MapOverlay, MapView                                                                 |

`ControlCluster` is item #4 of the eleven ranked in `docs/sdk-module-primitives.md`, so it is already
on the list independently.

## 4 · What is missing

### 4.1 · The number that matters

Of the **eleven** primitives ranked in `docs/sdk-module-primitives.md` on 2026-09-05, **one is done**
— MapControlButton's State axis. Items #2–#11 are all not-started a week later: attribute section,
in-surface status message, control cluster, meta strip, drag handle, step list with connector,

The library did not lack a list. It lacked anyone building from it.

### 4.4 · Verified absent at feature level

```
Progress: thickness axis + indeterminate   nothing in Progress.tsx
prefers-reduced-motion / useReducedMotion  nothing in packages/react/src or packages/tokens/src
```

**The dense type step is not missing from the tokens — it is missing from `Text`.**
`Primitives.Typography.font.size` already carries the small steps:

```
0=8  50=10  100=11.008000373840332  200=13.008000373840332  300=16  400=20  500=24  600=30 …
```

`Text` exposes nothing below `text-xs`, so the 8, 10 and 11px steps are unreachable from the
component. Two of them also still carry the floating-point noise `docs/gap-audit-2026-09-05.md`
recorded — `11.008000373840332` and `13.008000373840332` — in the token source itself, not a
generated file. That is a token fix and a `Text` axis, not a new component.

> An earlier draft of this document said "no fontSize scale found in tokens-light.json". That was
> wrong: the probe looked for a key named `fontSize` and the scale is at
> `Primitives.Typography.font.size`. Corrected before publishing.

The glass surface role is a special case: a `glass` token exists in `tokens-light.json:2641` and a
`.glass` utility in `tailwind.config.js:218`, yet FeedbackCard, RoutingInputGroup and
SaveLocationCard each still hard-code `bg-white/70` (one occurrence each, verified). The role exists
and nothing reads it.

### 4.5 · A live bug: every overlay animation is dead CSS

Found while checking whether an animation utility layer was missing. It is worse than missing — it
is referenced and absent.

Eight components ask for entrance and exit animations:

```
$ grep -rlo 'animate-in' packages/react/src/components
  Dialog  Drawer  FeedbackCard  Menu  Popover  Select  Toast  Tooltip
```

Tooltip, for example (`Tooltip.tsx:60`):

```
… shadow-overlay animate-in fade-in-0 zoom-in-95 data-[state=closed]:animate-out
  data-[side=bottom]:slide-in-from-top-2 …
```

None of those classes exist in the built stylesheet:

```
$ grep -o 'animate[a-z-]*' packages/react/dist/style.css | sort -u
  animate-ping   animate-pulse   animate-spin          ← Tailwind's three built-ins
$ grep -o '@keyframes [a-zA-Z-]*' packages/react/dist/style.css | sort -u
  @keyframes ping   @keyframes pulse   @keyframes spin
$ for c in animate-in fade-in-0 zoom-in-95 slide-in-from-top-2; do grep -c "\.$c{" packages/react/dist/style.css; done
  0  0  0  0
```

The cause: `tailwindcss-animate` is **not a dependency** of any package here, and
`tailwind.config.js`'s `plugins` array contains only the local `.glass` utility. The classes are
inert — every dialog, drawer, menu, popover, select, toast and tooltip in the library appears
instantly, with no transition, and has done so silently. Nothing catches it: the classes are strings,
so type-checking and tests pass, and Chromatic — the one gate that would show it — has been on its
snapshot limit since early September.

**Fix:** add `tailwindcss-animate` and register it in `plugins`, or define the keyframes and
utilities locally. Then extend `tokens:raw:check` or a new check to fail on a utility class that
emits no CSS, which is the general form of this defect.

This also settles the motion question in §4.2: the gap is not "an animation utility layer would be
nice", it is "the library already believes it has one".

### 4.6 · What the MAP-595 prototype had to draw itself

`apps/mapscale-review` uses 13 Kozmos components and hand-builds the rest. Per
`memory/mapscale-is-a-ds-playground-too.md`, its workarounds are design-system findings. Those that
are generic UI, not Map Content domain logic:

`PanelHeader` (eyebrow + leading icon + title + actions) · `SectionHeading` (10px uppercase overline)
· `SourcePill` (dot + label) → StatusDot · `SavedNotice` (map-anchored confirmation) → in-surface
status · `ExpertHoldBanner` → Banner · `ExpertHoldChip` (collapsible corner notice) ·
`AiMappingStatus` (status card) · `FloorPlanThumb` + `PreviewOverlay` → Thumbnail + Lightbox ·
`GeometryToolbar` + `Tile` → Toolbar + ToolButton · `WhyTip` (**tooltip on a disabled control** — the
DS Tooltip cannot do this) · selection-count pill · caption/refusal pill · `PrefRow` (label + trailing
Switch) · a floating map IconButton variant · Slider with a value readout.

Four of those are the same missing thing: **a status message that lives inside a surface.**

## 5 · Onboarding and notification overlays

**Notifications: yes, top tier.** In-surface status message is ranked #3 and hand-built four times in
one prototype. Banner and StatusDot each have a named consumer. A notification centre is composable
from Popover + List + Badge and does not need to be a component.

**Onboarding: not yet.** The evidence is one `Tour` component in one prototype. Coachmark and
Spotlight are composable from Popover + Backdrop today. Build when a second consumer asks.

## 6 · What's next, in order

0. **Fix the dead animation CSS (§4.5).** It is a one-line dependency, it affects eight shipped
   components, and it is the only item here that is a defect rather than a decision.
1. **Settle §1** — publish and get one consumer, or declare the system internal. Everything else is
   downstream, and the answer changes what "missing" means.
2. **Build eight parts**, in this order — each unblocks either an example or a prototype workaround:
   in-surface status message · Toolbar + ToolButton · DragHandle (lift out of BottomSheet) ·
   ControlCluster (generalise MapControlsGroup) · AttributeSection · MetaStrip / DescriptionList ·
   glass surface role (make the three cards read it) · Tooltip on disabled triggers.
3. **Make Figma slots real** — `productSdkSlot` → actual SLOT nodes — before promising slotted layouts.
4. **Then** build the five slotted layouts (§3.2) and the examples, and deprecate the 14 in place.
   Do not delete.

Not on this list, deliberately: the type-scale decision (14/12 join the scale or the library moves to
13/11) and Chromatic's snapshot limit are both still open from `docs/session-handoff.md` §4, and both
still gate visual work.

## 7 · What is not verified

Stated plainly, because the audit that produced §2.1 did not finish.

- **The 24 per-set verdicts were produced by one agent each and never challenged.** The workflow that
  was to run three adversarial refuters per finding hit its agent cap and died; 970 of 1000 agents
  failed. Treat the 14 relocations as a first pass, not a decision — particularly the four classed
  `composition-of-ds-parts` rather than `product-layout`, which is the softer call.
- **§4.2 and §4.3 are mine, mechanically re-verified** after the agents' taxonomy list proved to
  contain false gaps (it listed a generic announcer as missing while `NavigationAnnouncer` exists on
  three platforms, and a FloorSelector collapsed form as missing while iOS has one).
- **The two external findings in §1** — the Web SDK CSS and the three Figma libraries — were read by
  an agent outside this repo and are not re-verified here.
- **Nothing in this document was run against Figma.** No plugin run, no file read.
